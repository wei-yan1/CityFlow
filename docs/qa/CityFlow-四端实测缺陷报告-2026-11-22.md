# CityFlow 四端实测缺陷报告

- 日期：2026-11-22
- 环境：`DESKTOP-KPHLTQ1`，Windows，PowerShell 7.6.4
- 入口：`http://localhost:8087`
- 架构：Go + go-zero 六进程微服务；MySQL 3307、Redis 6380、PostGIS 5434、RabbitMQ 5673/15673
- 浏览器：侧边浏览器，1280×960
- 测试方式：浏览器真实点击 + 页面内同步请求 + 服务日志 + MySQL 数据核对

## 1. 结论

两轮四端实测加一轮针对性回归，共确认 **22 项问题**：P1 5 项、P2 11 项、P3 6 项；其中 19 项已复现/有代码或数据证据，3 项为待确认的低优先级现象。

> 复核更新（2026-11-23 00:08）：原始 22 项均已按当前代码、数据库和页面重新复核；每项的最终状态、处理方式和验证证据见文末「10. 复核结果」。本文前面的复现记录保留原样，作为修复前的证据。

主链路整体可以走通：用户发单 → 支付 → 骑手接单 → 单取件点/双取件点履约 → 完成 → 用户评价；商家建店、平台审核与治理页面也都能打开。但支付优惠、支付与订单一致性、实时位置、评价归属、骑手履约统计这 5 条链路存在高优先级缺陷，其中 3 条会直接造成“页面不能正常显示/功能不可用”，2 条会造成业务数据污染。

## 3. 高优先级缺陷（P1）

### CF-001 任务支付时可用券查询 404，优惠券完全不可用

- 端：用户端
- 页面：发布任务 → 支付弹窗
- 严重度：P1
- 现象：支付弹窗固定显示“可用券查询失败，可先按原价支付。”；用户已有券，但没有一张能用于任务支付。
- 复现：
  1. 用示例用户登录，进入 `/user`，发布一笔 PICKUP 任务。
  2. 点支付，在支付弹窗观察优惠券区域。
  3. 对 `d5a5d592-5856-42c2-aabf-9261240cb615`、`6a946142-10bf-41b1-b855-95c272c7cd71` 复测，结果一致。
- 证据：
  - `GET /api/v1/coupons/task/d5a5...` → 404；`GET /api/v1/coupons/task/6a946...` → 404。
  - `gateway.err.log` 同时出现 `order.Order/Get id:"d5a5..."`、`id:"6a946..."` 的 `code = NotFound desc = order not found`。
- 代码定位：`app/gateway/cmd/api/internal/handler/orders.go` 的 `ListOrderCoupons` 把路径里的 `taskId` 直接当作 `orderID` 去查订单；任务支付没有建立 taskId→orderId 的映射，因此必查不到。
- 影响：优惠券是用户核心权益，当前任务支付实际只能原价支付；领券、我的券页面正常反而放大了“券不能用”的落差。
- 修复建议：按 `task_id` 查订单，或在任务支付创建订单时写入 task 关联；补一条“任务支付可用券”集成测试。

### CF-002 支付成功后 `Order.MarkPaid` 404，订单状态与支付状态不一致

- 端：支付 / 订单（影响用户、平台）
- 严重度：P1
- 现象：支付侧显示成功，但 payment 日志出现 `Order.MarkPaid ... order not found`；订单侧没有对应记录的状态回写。
- 复现：对 `d5a5...`、`6a946...` 两次任务支付后检查 payment 错误日志，均复现。
- 证据：`payment-1.err.log` 中 2 条 `order.Order/MarkPaid` NotFound，ID 分别是 `d5a5...` 和 `6a946...`。
- 代码定位：`app/payment/application/payment/payment_service.go:142` 把 `paid.TaskID` 传给 `Order.MarkPaid`，第 146 行又忽略 `domain.ErrNotFound`。
- 影响：支付成功与订单已支付状态脱节，后续退款、对账、统计和平台任务状态都可能不一致；这不是单纯日志噪声。
- 修复建议：支付记录里保存真实 orderId，或由 Order 侧按 taskId 幂等落单；`ErrNotFound` 不应静默吞掉，应进入可重试对账队列。

### CF-003 任务位置流 WebSocket 稳定 403，地图实时位置不可用

- 端：用户端、骑手端
- 页面：任务地图 / 历史轨迹弹窗
- 严重度：P1
- 现象：地图弹窗能打开，但始终显示“该任务还没有位置记录”；WebSocket 位置流握手返回 403。
- 复现：
  1. 骑手登录 `/rider`，打开任务地图或历史轨迹。
  2. 页面请求 `/api/v1/tasks/<id>/location/stream`，浏览器 WebSocket 关闭码 1006。
  3. 用同一骑手令牌手工连接，仍关闭；换无效令牌后网关日志变为 401。
- 证据：
  - 截至 19:57，Gateway 共 194 条 403，全部集中在位置流：`7ed77...` 170 条、`6a946...` 16 条、`d5a5...` 8 条。
  - 同一骑手 JWT 解码为 `sub=00000000-0000-4000-8000-000000000003`、`role=RIDER`；任务 `6a946...` 的 `worker_id` 也是 `...003`，归属一致。
  - 同一令牌请求 REST `/api/v1/tasks/6a946.../location` 返回 404；无效令牌的 WebSocket 返回 401，说明流式链路不是“完全没带令牌”。
- 代码定位：
  - `app/tracking/cmd/rpc/internal/stream/stream.go` 从 `Sec-WebSocket-Protocol` 取 bearer，`CanTrack` 失败时 `writeStreamError` 返回 403。
  - `app/tracking/application/tracking/tracking_service.go:299` 做 ADMIN / 任务创建人 / 任务 worker 三类鉴权；第 302 行状态比较用的是 `"Open"`、`"Completed"`、`"Cancelled"`，而接口/数据库实际是 `OPEN`、`COMPLETED`、`CANCELLED`。
  - 归属和角色表面一致却仍 403，说明流式链路的 claims/任务快照与 REST 链路存在不一致，需在 `CanTrack` 前后打印 claims 和 task worker/status 做一次定位。
- 影响：用户看不到骑手实时位置，骑手看不到自己的轨迹；任务地图核心功能名存实亡，也会影响异常取证。
- 修复建议：先用一笔 CLAIMED/PROCESSING 任务复现并记录 claims、task.worker_id、task.status；统一状态大小写常量；补 WebSocket 鉴权集成测试（RIDER、USER 创建人、ADMIN、无关 USER 四种身份）。

### CF-004 POI 被当成商家，已完成订单可写“商家评价”并污染平台审计

- 端：用户端 / 平台端 / 商家端
- 页面：地图 POI 详情、已完成订单评价、平台评价审计
- 严重度：P1
- 现象：高德 POI“桂林北站”被渲染成商家详情页（“店 / 桂林北站 / 暂无评分 / 商家介绍 / 用户评价”）；普通 POI 评价被后端 400 拒绝，但在已完成订单里点“评价商家”却保存成功，并作为商家评价进入平台审计。
- 复现：
  1. 地图搜索“桂林北站”，打开右侧 POI 详情，提交评分/评价 → `POST /api/v1/places/amap/B030501C8B/reviews` 返回 400“评价必须关联一笔已完成的订单”。
  2. 打开已完成任务 `d5a5...` 的评价区，提交“取件点被当成商家评价。” → 页面提示“商家评价已保存。”。
  3. `GET /api/v1/tasks/d5a5.../merchant-review-target` 返回商家 `{"source":"amap","id":"B030501C8B","name":"桂林北站"}`。
  4. 平台评价审计出现该条记录。
- 证据：`cityflow_discovery.place_reviews` 新增记录：
  - `id=4e01360ce115f24a7b7fd384bea7e93a`
  - `order_id=d5a5d592-5856-42c2-aabf-9261240cb615`
  - `place_source=amap`，`place_id=B030501C8B`
  - `user_id=00000000-0000-4000-8000-000000000001`
  - `rating=5`，`comment=取件点被当成商家评价。`
- 影响：非商家 POI 获得商家评分；用户评价被写进错误实体；平台审计出现无效数据；商家侧又看不到这条评价，形成“审计有、商家无”的割裂。
- 修复建议：`merchant-review-target` 只允许返回真实 `merchant_profiles`；订单评价必须校验订单里确实包含该 merchant；POI 评价与商家评价拆成两套接口/表，禁止用 `place_reviews` 承载商家评价。

### CF-005 骑手累计完成始终 0 单，平台骑手资料也显示 0

- 端：骑手端、平台端
- 严重度：P1
- 现象：骑手完成多笔任务后，首屏仍显示“累计完成 0 单”；平台骑手资料同样 0；`GET /api/v1/riders/me` 返回 `completed_tasks:0`。
- 证据：
  - 数据库 `cityflow_task.tasks` 中该骑手 `worker_id=...003` 的 `COMPLETED` 任务共 3 笔。
  - `rider_profiles` 中同一 `user_id` 的 `completed_tasks=0`。
  - 代码 `app/task/internal/adapter/mysql/task_repository.go:262-264` 注释明确 `rider_profiles` 是只读视图，完成计数属于未来 rider/identity event flow，尚未实现。
- 影响：骑手看不到真实履约量，平台无法按完成单量做激励/考核；结算金额正常但统计为 0，可信度受损。
- 修复建议：任务完成事件写 rider 统计投影，或查询时按 `worker_id + COMPLETED` 聚合；补“完成 2 单后累计完成=2”的集成测试。

- 端：用户端、骑手端、平台端
- 现象：种子任务和骑手资料出现 `æ¡‚æž—ç”µå­...`、`éªŒæ”¶éª‘æ‰‹` 一类 mojibake；新建任务地点显示正常。
- 证据：用户任务列表、平台任务表、骑手任务卡、骑手名/服务区域均可见；新任务 `6a946...` 的中文地点正常。
- 判断：历史种子数据写入时 UTF-8 被二次编码，或导入连接字符集不对；不是浏览器字体问题。
- 影响：骑手看不清取送地址，平台表格不可读。
- 修复建议：修正 seed/导入脚本的 `utf8mb4` 连接与文件编码；对现有 dev 数据重灌或做一次性转码校验。项目允许不保留旧数据，可优先重灌。

### CF-007 未支付任务出现在骑手“附近可接”列表，且可点击接单

- 端：骑手端
- 现象：`新库验收任务`（`86a4708d-3d97-4fd5-aa39-533d7ea44aa9`，OPEN，¥20.00，未支付）出现在附近列表，按钮为“接下任务/立即取件”；点击后服务端返回 409“任务尚未收到付款，暂不能接单”。
- 判断：服务端拦截正确，前端没有过滤未支付任务，也没有“未支付”标记或禁用态。
- 影响：骑手白跑一趟、反复点击；任务列表可信度下降。
- 修复建议：列表接口只返回已支付 OPEN 任务，或前端显示“待用户支付”并禁用接单。

### CF-008 双取件点整单状态冗余且与取件进度矛盾

- 端：骑手端
- 现象：两个取件点都确认 `PICKED_UP` 后，整单仍是 `CLAIMED`，页面仍提示“更新整单状态：已到达取件点”；必须再手动点两次（CLAIMED→ARRIVED→PROCESSING）才出现“确认送达”。
- 证据：任务 `6a946...` 的事件流显示两个 `PICKUP_n_PICKED_UP` 后，才出现 `CLAIMED→ARRIVED→PROCESSING→COMPLETED`。
- 影响：骑手以为没取完，重复操作；状态机与取件点状态两套口径不一致。
- 修复建议：整单状态由取件点进度推导，或在全部取件点 PICKED_UP 后自动进入 PROCESSING；前端只保留“确认送达”一个关键动作。

### CF-009 商家可把每小时容量设为 0，仍显示营业中

- 端：商家端
- 现象：编辑门店把容量改为 0，保存成功，页面显示“营业中 / 每小时容量 0 单”；之后已恢复 100。
- 代码：`app/discovery/application/merchant/merchant_service.go:122` 只校验 `CapacityPerHour < 0`，0 合法；前端输入 `min=0`。
- 影响：营业中但零容量，接单/排期语义矛盾；如果后续按容量限流，会直接卡死门店。
- 修复建议：`OPEN` 时容量必须 ≥1；容量 0 自动转为 PAUSED，或前后端都拒绝 0。

### CF-010 新建门店不出现在用户地图搜索，只能看到地图点位

- 端：商家端 / 用户端
- 现象：新建 `桂电金鸡岭校园便利店` 后，用户地图搜索精确店名没有本地门店结果，只返回高德 POI；地图图层上能看到“店”点位。
- 判断：`/api/v1/map/search` 走的是高德搜索，本地商家未进入搜索索引；门店可发现性缺口。
- 影响：商家建完店，用户搜不到，交易入口断。
- 修复建议：地图搜索增加本地商家结果合并，或提供“附近商家”独立入口并保证新店可检索。

### CF-011 骑手评价数不同步：订单卡片 0 条，评价区 1 条

- 端：骑手端 / 订单详情
- 现象：同一订单详情页，骑手卡片显示“★ 5.0 0 条评价”，下方“评价”区显示“1 条评价”且有最近评价内容；骑手公开资料也没有评价数。
- 判断：评价写入成功，但骑手公开资料的 `review_count` 未同步/未计算。
- 影响：骑手信用展示错误；用户无法判断服务口碑。
- 修复建议：评价完成后更新骑手评价聚合，或详情页从同一评价数据源计算。

### CF-012 已完成任务的取件点仍显示“待取件”

- 端：骑手端
- 现象：单取件点任务 `d5a5...` 已完成，任务地图弹窗仍显示“取件点 · 待取件”；双取件点在“已到达/进行中”阶段也有状态滞后。
- 影响：地图信息和任务状态不一致，骑手/用户对进度判断错误。
- 修复建议：地图取件点状态从 `pickup_stops[].status` 和整单状态统一映射，完成后显示“已取件/已完成”。

### CF-013 平台任务调度“发布用户”列显示 UUID

- 端：平台端
- 现象：任务调度表发布用户列显示 `00000000-0000-4000-8000-000000000001`，不是姓名/昵称。
- 影响：运营无法快速识别发布者，排查任务要多跳一次。
- 修复建议：关联 identity 显示昵称/手机号脱敏；至少显示“示例用户（0001）”。

### CF-014 平台建号/骑手注册审核不校验邮箱、手机号格式

- 端：平台端
- 现象：
  - 平台新建商家账号 `测试商家账号`，手机填 `123`，创建成功并进入账号列表。
  - 骑手注册申请 `123`、邮箱 `123@q`、手机 `123123`、支付 ¥0.01、凭证 `1231231321`，被“核验并开通”成功，骑手资料出现“123”。
  - 直接 API 用弱密码 `abc` 返回 400，说明后端 8 位密码校验存在；邮箱/手机格式仍无校验。
- 影响：脏账号、测试账号、无法联系的用户进入系统；骑手审核通过后可能影响结算/通知。
- 修复建议：邮箱、手机号、凭证做格式与唯一性校验；审核页展示校验结果，管理员不能只靠肉眼。

### CF-015 平台任务状态文案重复/矛盾

- 端：平台端
- 现象：取消的“校医院代购感冒药”显示“已取消 · 等待接单”；待接单任务显示“待接单 · 等待接单”；地图任务下拉同样重复拼接。
- 判断：状态标签和状态描述用了同一字段拼接两遍，且“已取消”还带“等待接单”是语义错误。
- 修复建议：状态映射表输出单一文案；已取消不再显示等待接单。

### CF-016 已完成/已取消任务的状态校验字符串大小写不一致（代码级）

- 端：Tracking / 任务地图
- 现象：`CanTrack` 用 `item.Status == "Open" / "Completed" / "Cancelled"` 判断，而数据库/接口实际是 `OPEN` / `COMPLETED` / `CANCELLED`。
- 影响：已完成/已取消任务不会被状态分支拦截；如果这些任务还留有最后位置，授权用户/骑手仍可能读到历史位置，属于隐私边界缺陷。
- 判断：代码级确认；本次未构造“已完成且有位置”的数据来验证实际泄露，故不升级为 P1。
- 修复建议：统一使用 domain 常量；补“COMPLETED/CANCELLED 不可订阅位置”的测试。

## 7. 非缺陷/自动化噪声

以下现象已在测试中出现，但不作为产品缺陷：

- `/favicon.ico` 404 149 次：浏览器默认请求，非接口问题。
- 任务没有位置记录时 `/location` 返回 404：属于“暂无位置”的正常分支；但 WebSocket 403 是另一件事（CF-003）。

- 负价 API 返回 400、前端 `min=0.01` 拦截：校验正常，不作为缺陷。
- 浏览器未授权地理位置导致“定位未成功，可继续浏览桂林市：定位超时”：自动化环境限制，非产品问题。
- 商家建店前 `/api/v1/merchants/me` 404：正常。
- 原生 `confirm` / `prompt` 会卡住浏览器自动化：属于自动化体验问题，不是功能缺陷；产品侧可考虑统一自定义弹窗。
