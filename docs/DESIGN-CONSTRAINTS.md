## 1. 项目仍在开发阶段：允许破坏性重构

- 当前没有需要保留的旧数据。表结构、领域模型、API、页面、目录结构和业务逻辑都可以大幅增删，不必为了“以前实现过”而保留。
- 不设计过渡期方案：不做旧表兼容、旧接口双写、旧数据回填、旧库视图、版本迁移适配、灰度双跑。新设计直接落到最终形态。
- 迁移只要求空库或当前开发库能启动。开发库可以直接重建；不要新增只为兼容旧列、旧记录或旧接口的补丁。
- 现有 `legacy` / 兼容别名只服务当前页面，属于待清理的历史代码，不作为新设计模板；新功能不要再造第二套接口别名。
- **“不保留旧数据”不等于授权删除现有数据库或工作区文件。** 清理具体数据、删库、删用户文件仍要按具体任务判断，不能顺手执行。

## 3. 契约、路由和目录

- `gateway.api` 是 Gateway 的 HTTP 契约来源，各服务 `cmd/rpc/*.proto` 是 RPC 契约来源；契约变更必须同步文档和前端调用。
- Gateway 当前由 `routes.go` 手工维护路由表，并与 `gateway.api` 镜像；新增/删除路由必须同时改两处，并执行 `goctl api validate`。不要只改其中一处。
- Handler 只负责解析请求、调用服务和写响应；业务规则放在该服务 `application/`，数据库/缓存实现放在该服务 `internal/adapter/`，不要反过来。
- 目录调整按 `docs/architecture/project-layout.md` 的十服务结构走：服务私有代码放 `app/<service>/`，多服务共享技术组件放 `internal/platform/`，稳定契约与通用值对象放 `internal/common/`。`reaction` 是独立服务（`app/reaction`，端口 `8097`），拥有点赞状态与批量投影；内容服务只消费 `like_count`。不要在 `app/` 下恢复已删除的旧单体入口、旧 `cmd` 或旧 `internal/application|domain|infrastructure` 分层。

## 10. 容量与代码质量硬约束

- 目标：2 台机器、2 个 16 GB 内存、两个 i5-13700HX，按 10 万 QPS 设计；10 万是压测目标。
- 10 万 QPS 只靠缓存、批量、异步、静态化：能缓存的绝不回源，能批量/异步的绝不同步，禁止 N+1、全表扫描、深 offset。
- 请求必须有超时；禁止无界 goroutine/队列；过载直接 429/503；列表必须分页并限制 `limit`。
- 写接口必须幂等（唯一键/幂等键）；高频写走 Outbox、重试、死信、幂等消费；每个服务设 `GOMEMLIMIT`、连接池上限（建议 ≤30）、请求体上限。
- 代码按大厂底线：边界清晰、错误不吞、资源必释放、并发跑 `go test -race`、日志/指标/pprof 可查、契约与前端同步。
- 性能结论必须有压测：吞吐、p50/p95/p99、错误率、CPU/内存、GC、连接池、慢查询；没有数据不许写“已支持 10 万 QPS”。
